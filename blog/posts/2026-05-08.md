# Improving Field Photo Transfer

Over the past couple years, I've been very lucky to be able to attend Disaster Situational Assessment & Reconnaissance (DSAR) trainings through MO TF-1. The Missouri Task Force 1 DSAR team is leading the way when it comes to using drones for Reconnaissance, and they are writing the playbook for how drones are used, how photos are transferred and processed, and more. Along the way, I've also met some members of the National Alliance for Public Safety GIS Foundation (NAPSG), who are instrumental in developing the Search & Rescue Common Operating Platform (SARCOP) for first responders, and search and rescue teams. Primarily, Adam Fackler, who was also at the Esri Developer & Technology Summit.

Earlier this week, Adam brought me a problem that these drone teams are facing. The process of going from drone photos on an SD card to clean points on a map with attached images is not a smooth one. 

Right now, it takes the drone team landing, offloading the SD card, taking the SD card to someone with a laptop/desktop, which needs to have ArcGIS Pro (Desktop software) and a custom python geoprocessing tool installed, and then running that tool on the images to generate multiple copies of the images, and creating a feature layer in a geodatabase, which can be uploaded into ArcGIS online as it's own layer, or have it's features copied into an existing dataset.

In a field where every minute matters, these barriers to getting clean data available to command staff and other field teams pose a real challenge. I've been working on building custom widgets for ArcGIS Experience Builder Developer Edition for almost a year now, and after me bringing it up at the Dev & Tech summit earlier this year, Adam asked for my help in seeing if a custom widget could lower the barrier to entry for a field team. For me, this is a dream request because:

1. The framework is there already (Custom python tool)
2. The constraints are simple and well defined
3. It was easy to test: Adam provided testing data (Photos)
4. There is impact (real search and rescue team workflows might be improved)

I began on the request as soon as I got home from work that day, and by that night, I had a fully functional (albeit not field tested) widget, with responsive UI ([Thank you calcite](https://developers.arcgis.com/calcite-design-system/components/)) and quick load times. The end result is super simple. You select your photos (individually, or select a whole zip file), define some attributes that you want stamped for these features (Like strike team, ID, drone type, etc) can view the photos as preview points on a map before uploading as a sanity-check, and then you can upload photos one at a time, or all at once. There's even notifications in the form of calcite-alert messages, and per-photo status information through calcite-chip components on each image.

The widget isn't fully ready yet. I am really excited to provide the widget for free, for any organization to use, but due to the robust nature of how Situational Assessment & Reconnaissance teams need to operate, I am leaving the widget in an unverified alpha version for now. It's still available for organizations to download and test, but I don't recommend using it in a large scale deployment without significant testing and code-review. If you or your organization does end up using the widget, I would appreciate feedback on how it can be improved, as well as any testing results, as it would benefit a wide community of users.

## I want to use it!

If you're interested in using the photo-dump widget, even in it's untested, unverified state, you can find it in my [public widgets repository](https://github.com/SunshineLuke90/widgets). As of the time of this blog post, it's sitting on the [photo-dump branch](https://github.com/SunshineLuke90/widgets/tree/photo-dump), but if it's been tested and ready for a beta or production release, you'll be able to find it in the main branch of the repository.

Please provide feedback! Since the widget is in alpha, things are open to change, and I want to create a robust tool. If you're a developer yourself, feel free to make a pull request, or if you have testing feedback, please leave an issue on the GitHub repository.
