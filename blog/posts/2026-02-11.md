# Calendar in Experience Builder

I have needed a calendar view of data many times for feature services in my ArcGIS application building. List widgets are great for a variety of use cases, but they aren't good with time based data. This is because clusters of events in a time period will be spaced evenly apart, and large gaps in time between data points will be obscured. Displaying data on a chart might be a good way to show these gaps or clusters in time, but then you lose any information on the events themselves.

_For data on events, a calendar is really the best way to display that information succinctly._

## Setting up the Feature Service

Just as big a factor as developing a good custom calendar widget is setting up a the schema for the feature service in a way that is conducive to display on a calendar. When thinking of the different ways to display an event on a calendar, there are effectively 2 different ways to view a calendar, and 2 different ways to display an event on a calendar.

#### _Calendar Display_

- Day View: Each slot on the calendar is one day, with no markings for time. Events are displayed as a list within each day, irrespective of time. ![A screenshot of the Calendar Widget in Month View](/blog/images/CalendarMonth.png)
- Time View: Each slot on the calendar is a full day, and 24 hours of the day can be viewed. Events are displayed based on the amount of time that they take up. ![A screenshot of the Calendar Widget in Week View](/blog/images/CalendarWeek.png)

#### _Event Display_

- Time Based: The event is displayed in time view, as a large item with a start and end time. ![A screenshot of a start and end event](/blog/images/CalendarEventTime.png)
- All Day: The event is displayed as a header on the day, with no start or end time.![A screenshot of an all day event, in the header of a time view week](/blog/images/CalendarAlldayHeader.png)

Based on this, I needed a way to guarantee that events will display appropriately on a calendar, following these rules. While I could have separate fields based on whether the event falls into the _Time Based_ or _All Day_ category, it's easier to simply reuse fields, and have the widget determine how to handle the information. I only needed 3 fields:

- Start Date (Combined Date & Time field)
- End Date (Combined Date & Time field)
- AllDay (A string, playing as a boolean y/n)

## Integrating Fullcalendar.io

The whole calendar widget is based on the open source [Fullcalendar.io](https://fullcalendar.io) calendar library. I am not good enough to write a full calendar UI from scratch, so I just looked for the easiest to use javascript calendar library that had support for react, and [Fullcalendar.io](https://fullcalendar.io) was the most popular option I could find. Fullcalendar has a very simple integration procedure.

### Reusability

For an Experience Builder widget, where the widget needs to be able to be re-used in other environments, it's as simple as initializing an npm project in the specific widget's folder, and then installing the specific npm packages into the widget's folder. This way, when the widget is pulled into a project, or automated deployment, all node modules can be downloaded appropriately.

### Styling

With the Fullcalendar integration, I needed to create a custom css file to convert fullcalendar css variables to variables used by the Experience Builder style system. This way, the calendar can be easily integrated into any application without having to modify the widget itself. I have used Experience Builder styling on many of my other widgets, but this was the first time integrating that styling pattern into something that had already been built and styled.

### Loading Events

To get events to load and display in the calendar, I had to learn to integrate with data sources, which are part of the Experience Builder framework. Data sources are a useful way to load data, share feature selection, and share filtering across multiple widgets. Because data sources are used, it makes it easy to select features across Experience Builder.

When a data source gets loaded, some data formatting gets applied to transfer the fields from the data source into the format required for fullcalendar. This is where the All Day field gets used, and when the label, description and symbology are applied to event objects.

## Using the Calendar in an App

I've found a couple of patterns for using the calendar widget in an application that have worked well. One of those patterns is on display in the demo Experience Builder app, found at [exb.luciuscreamer.com](https://exb.luciuscreamer.com/calendar). This application uses a map widget, and a feature information widget, organized in a grid widget. When a feature is selected, the feature information widget displays the popup, and the map widget zooms the map to the feature. Optionally, the map could filter the data source on map zoom, using a message action on the map widget.

The other pattern would be a fully non-spatial implementation, making the calendar take up the full screen, with a filter widget in a widget controller or hidden in a sidebar. This would allow the use of an ArcGIS feature service to populate a calendar, while not overwhelming the user with extra features/functionality.
